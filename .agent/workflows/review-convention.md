## 코드 리뷰 규칙

### 1. API 오류 응답 원칙

- 새로 추가되거나 변경되는 API 오류 응답은 RFC 9457 / Problem Details 원칙을 따라야 한다.
- 다음과 같은 경우는 기본적으로 리뷰 지적 사항이다.
	- 문자열 body를 직접 반환하는 오류 응답
	- 모듈 내부 전용 ad hoc error DTO를 새로 만드는 경우
	- 기존 Problem Details 전환 흐름과 무관한 새로운 오류 응답 형식을 추가하는 경우

### 2. 예외 허용 조건

- 아래 조건을 모두 만족할 때만 임시 예외를 허용한다.
	- 하위 호환이 명확하게 필요하다.
	- 왜 예외가 필요한지 설명할 수 있다.
	- 최종적으로 Problem Details로 수렴하는 전환 경로가 문서나 계획에 남아 있다.

### 3. 리뷰 시 확인 항목

- 상태 코드는 적절한가
- 오류 응답이 `ProblemDetail` 또는 이에 준하는 공용 생성 경로를 사용하는가
- `status`, `detail`이 일관되게 내려가는가
- `instance`, `type`, `code` 같은 확장 필드를 쓰는 경우 프로젝트 규칙과 맞는가
- 기존 클라이언트 호환 때문에 예외를 두었다면 그 범위가 최소화되어 있는가
- DDD + 헥사고날 아키텍처 경계를 존중하는가
- 애플리케이션 계층이 웹, DB, 외부 인프라 세부사항에 직접 결합되지 않는가
- 포트와 어댑터 책임이 적절히 분리되어 있는가
- 변수명, 메서드명, DTO명, 포트명 등이 역할과 의미를 명확하게 드러내는가
- 축약어, 모호한 이름, 문맥 없이는 의미를 알기 어려운 이름이 새로 도입되지 않았는가

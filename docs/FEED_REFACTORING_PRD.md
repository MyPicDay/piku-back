# Feed Refactoring PRD

작성일: 2026-03-08

## 문서 목적
- Feed 조회 경로를 대규모 트래픽 기준으로 리팩토링하기 위한 실행 계획을 정의한다.
- 구현 순서를 `task` 단위로 분리하고, 각 task마다 권장 커밋 메시지를 함께 제시한다.
- 이번 문서는 설계와 작업 분해가 목적이며, 코드 구현 자체는 포함하지 않는다.

## 문제 요약
- `FeedQueryService`가 캐시 처리, 후보 수집, 추천 적용, 페이징, DTO 조립을 모두 담당하고 있다.
- 친구 피드와 공개 피드를 메모리로 크게 적재한 뒤 다시 정렬하고 잘라내는 구조라서 트래픽이 커질수록 응답 시간이 급격히 나빠진다.
- 목록 응답 조립 단계에서 사진, 유저, 친구 상태, 댓글 수를 항목별로 조회해 서비스 레벨 반복 조회가 발생한다.
- 캐시 hit 경로도 `id 목록 -> 엔티티 재조회 -> 필터링` 구조라 정렬 보존과 범위 제어가 약하다.

## 현재 구조에서 가장 큰 병목
- 전체 후보 적재 후 메모리 페이징
- DTO 조립 단계의 반복 조회
- 친구 ID 수집과 피드 조회 요구사항이 섞인 cross-context 재사용
- 캐시된 추천 순서 보존 불명확

## 목표
- Feed 조회를 `후보 수집`, `정렬/추천`, `목록 응답 조립`으로 분리한다.
- 서비스 계층은 orchestration만 담당하고, 반복 조회와 조합 책임은 outbound adapter로 내린다.
- 피드 목록 응답은 전용 조회 포트와 application read model로 구성한다.
- 페이지 크기가 커져도 쿼리 수와 메모리 사용이 선형 증가하지 않도록 만든다.

## 비목표
- 추천 알고리즘 자체의 점수 공식을 이번 작업에서 바꾸지 않는다.
- 피드 상세 조회는 목록 경로 안정화 이후 별도 task로 다룬다.
- Redis 캐시 정책 전체를 재설계하지는 않고, 현재 피드 조회 요구사항에 필요한 범위만 정리한다.

## 대상 범위
- `src/main/java/com/pikume/back/feed/application/service/FeedQueryService.java`
- `src/main/java/com/pikume/back/feed/application/service/FeedCandidateCollector.java`
- `src/main/java/com/pikume/back/feed/application/service/FeedCompositionService.java`
- `src/main/java/com/pikume/back/feed/application/port/out/*`
- `src/main/java/com/pikume/back/feed/adapter/out/*`
- Feed가 의존하는 `Diary`, `Social`, `User`, `Recommendation` 조회 어댑터 일부

## 설계 원칙
- 조회 유스케이스 단위의 전용 조회 포트를 만든다.
- 반환 타입은 엔티티나 Web DTO가 아니라 application read model로 둔다.
- 서비스는 목록을 순회하며 단건 포트를 반복 호출하지 않는다.
- adapter는 `JOIN`, `IN`, `GROUP BY`, 배치 조회 조합을 사용해 read model을 구성한다.
- 캐시 경로와 non-cache 경로가 같은 read model 계약을 사용하게 만든다.

## Task 1. 피드 목록 응답 전용 조회 포트 도입
### 작업 내용
- 피드 목록 응답에 필요한 필드를 담는 `FeedListItemView` read model을 정의한다.
- `LoadFeedListViewPort`를 추가한다.
- 목록 응답에 필요한 사진, 작성자 정보, 친구 상태, 댓글 수, 좋아요 수, liked 여부를 전용 조회 포트로 이동한다.
- `FeedQueryService.getAllDiaries()`는 더 이상 항목별 단건 포트를 직접 호출하지 않도록 바꾼다.

### 기대 효과
- 서비스 계층 반복 조회 제거
- 목록 응답 조립의 책임 분리
- 이후 후보 수집/캐시 경로와 결합하기 쉬운 구조 확보

### 완료 기준
- `getAllDiaries()`가 read model 기반으로 동작한다.
- 서비스 내 `for/map` 루프에서 사용자/사진/댓글/친구상태 단건 조회가 사라진다.

### 권장 커밋 메시지
- `refactor: 피드 목록 조회를 전용 조회 포트와 read model 구조로 전환`

## Task 2. 친구/공개 후보 수집을 ID 기반 조회 구조로 전환
### 작업 내용
- `FeedCandidateCollector`가 `List<Diary>` 전체를 조합하는 대신 `List<Long>` 또는 후보 전용 read model만 다루게 변경한다.
- 친구 피드와 공개 피드 후보 수집을 DB 조회 포트로 이동한다.
- 현재 `FriendUseCase.findFriendIdList()` 재사용 대신 피드 전용 친구 ID 조회 경로를 둔다.
- 본인 일기 제외, 읽음/미읽음 분리, 친구/공개 우선순위 적용 책임을 더 작은 단위로 나눈다.

### 기대 효과
- 전체 엔티티 적재량 감소
- friend DTO 경로 재사용에 따른 불필요한 조합 제거
- 후보 수집의 목적이 명확해짐

### 완료 기준
- 후보 수집 단계에서 친구/공개 전체 엔티티를 메모리에 쌓지 않는다.
- 피드용 친구 ID 조회가 친구 목록 DTO 조립 경로와 분리된다.

### 권장 커밋 메시지
- `refactor: 피드 후보 수집을 ID 기반 조회 포트 구조로 전환`

## Task 3. 전체 후보 적재 후 수동 페이징 제거
### 작업 내용
- 현재 전체 후보를 계산한 뒤 `subList`로 잘라내는 구조를 제거한다.
- 캐시 miss 경로에서 필요한 범위의 candidate window만 조회하도록 바꾼다.
- 추천 결과도 전체 후보가 아니라 제한된 범위에서 계산하도록 정리한다.
- 친구/공개 비율 유지가 필요하면 window 내부에서만 적용되게 만든다.

### 기대 효과
- 페이지 크기가 작아도 전체 후보 수만큼 메모리와 CPU를 쓰는 구조 제거
- 피드 조회의 p95/p99 개선

### 완료 기준
- `Pageable` 요청 시 필요한 범위만 조회하고 정렬한다.
- 전체 후보를 모두 적재하는 메모리 페이징 코드가 사라진다.

### 권장 커밋 메시지
- `refactor: 피드 조회의 전체 적재 후 수동 페이징 구조 제거`

## Task 4. 캐시 hit 경로 정렬 보존과 범위 조회 보정
### 작업 내용
- 캐시에 저장된 diary id 목록의 정렬 순서를 보존하도록 materialize 경로를 정리한다.
- `findAllById()` 결과 순서에 의존하지 않도록 명시적으로 재정렬한다.
- cache hit 시에도 필요한 범위만 조회하도록 바꾼다.
- 캐시된 id 중 삭제되었거나 접근 불가한 항목 처리 정책을 고정한다.

### 기대 효과
- 캐시 hit/miss 간 응답 순서 불일치 제거
- 불필요한 전체 entity 조회 제거

### 완료 기준
- cache hit 경로가 정렬과 페이지 범위를 안정적으로 보존한다.
- 캐시 항목 일부가 유효하지 않아도 응답이 깨지지 않는다.

### 권장 커밋 메시지
- `fix: 캐시 기반 피드 조회의 정렬 보존과 범위 조회를 안정화`

## Task 5. 상세 조회와 목록 조회 책임 분리
### 작업 내용
- `getDiaryWithPhotos()`는 목록 조회 최적화와 분리해서 다룬다.
- 목록용 read model과 상세용 read model의 책임을 나눈다.
- 상세 조회에서 필요한 접근 제어와 제한 응답은 유지하되, 목록용 조립 로직과 공유하지 않게 정리한다.

### 기대 효과
- 목록 경로 최적화가 상세 조회와 결합되어 흔들리는 문제 방지
- 이후 상세 조회 리팩토링 범위 명확화

### 완료 기준
- 목록/상세 응답 조립 코드가 서로 독립적으로 이해 가능한 구조가 된다.

### 권장 커밋 메시지
- `refactor: 피드 상세 조회와 목록 조회의 응답 조립 책임을 분리`

## Task 6. 피드 조회 회귀 테스트 보강
### 작업 내용
- 단위 테스트:
  - `FeedQueryService`가 전용 조회 포트만 사용하고 반복 조회를 직접 하지 않는지 검증
  - cache hit/miss 경로 계약 검증
- 통합 테스트:
  - `page size 1`과 `3`에서 쿼리 수가 선형 증가하지 않는지 확인
  - cache hit 시 정렬이 유지되는지 확인
  - 전체 후보 적재 제거 후에도 응답 순서와 내용이 보존되는지 확인

### 기대 효과
- 구조 회귀 방지
- 이후 추천/캐시 최적화 시 안전망 확보

### 완료 기준
- 피드 조회 관련 단위 테스트와 H2 기반 query count 테스트가 추가된다.

### 권장 커밋 메시지

## 리스크와 주의사항
- 피드는 댓글/친구/알림보다 구조가 크므로 한 커밋에 모든 변경을 몰지 않는 편이 낫다.
- 추천 점수 계산과 후보 수집 책임을 한 번에 바꾸면 원인 추적이 어려워지므로, 응답 조립과 후보 수집을 분리해서 진행해야 한다.
- cache hit 경로와 miss 경로가 다른 계약을 갖기 시작하면 다시 복잡해지므로, read model 계약은 반드시 하나로 유지하는 편이 좋다.

## 최종 완료 기준
- 피드 목록 조회가 전체 후보 적재 없이 동작한다.
- 목록 응답 조립이 전용 조회 포트 + read model 구조로 바뀐다.
- 서비스 레이어 반복 조회가 제거된다.
- cache hit/miss 모두 정렬과 범위가 일관된다.
- 페이지 크기 증가가 쿼리 수와 응답 시간에 직접 선형 비례하지 않는다.

# User Character ID Migration Runbook

- Status: Active
- Audience: Engineers, Operators
- Source of Truth: Yes
- Last Reviewed: 2026-08-11

## 목적

이 문서는 `users.avatar` 이미지 경로를 `users.character_id` 식별자 참조로 전환하는 단일 점검 시간 마이그레이션의 데이터 기준, 배포 확인과 실패 대응 절차를 정의한다.

## 변경 결과

- 기존 `users.avatar` 값은 같은 이미지 참조를 가진 고정 캐릭터의 `characters.id`로 변환한다.
- 문자열 비교는 대소문자와 공백 차이까지 구분하는 정확 일치다.
- 최종 `users.character_id`는 BIGINT NOT NULL이며 조회 인덱스를 갖는다.
- `users.avatar` 컬럼은 제거한다.
- User와 Character 사이의 데이터베이스 외래 키는 추가하지 않는다.
- 애플리케이션은 User 조회 시 Character 공개 일괄 조회 계약으로 이미지 참조를 해석한다.
- Pull Request에서는 실제 MySQL 컨테이너를 사용하는 전용 마이그레이션 테스트를 필수 실행한다.

## 마이그레이션 허용 데이터

각 사용자 행은 다음 조건을 모두 만족해야 한다.

- `users.avatar`가 null, 빈 문자열 또는 공백 문자열이 아니다.
- 이미지 참조가 정확히 일치하는 `FIXED` Character가 존재한다.
- 정확히 일치하는 `FIXED` Character는 한 건뿐이다.

AI 생성 캐릭터만 일치하거나, 대소문자만 다른 참조가 있거나, 같은 참조의 고정 캐릭터가 여러 건이면 마이그레이션을 진행하지 않는다. 임의의 캐릭터를 선택하거나 null로 대체하지 않는다.

## 점검 시간 절차

1. 이전 애플리케이션의 쓰기 트래픽을 중단하고 단일 점검 시간을 시작한다.
2. `users`, `characters`와 Flyway 이력을 포함한 데이터베이스 백업을 생성하고 복구 가능 여부를 확인한다.
3. 모든 사용자 avatar가 허용 데이터 조건을 만족하는지 확인한다.
4. null·공백·미일치·중복이 있으면 원인 데이터를 수정하기 전까지 배포를 중단한다.
5. Flyway V15를 적용한다.
6. `character_id` 백필 수와 전체 사용자 수가 같은지 확인한다.
7. NOT NULL, 인덱스, avatar 제거와 외래 키 미생성 상태를 확인한다.
8. 새 애플리케이션을 기동하고 로그인 사용자 정보, 프로필 단건, 사용자 검색과 피드·소셜의 아바타 표시를 점검한다.
9. 정합성 오류 로그가 발생하지 않는지 확인한 뒤 쓰기 트래픽을 재개한다.

이 전환에서는 경로 기반 이전 버전과 ID 기반 새 버전을 동시에 실행하지 않는다.

## 배포 전 자동 검증

- 일반 단위 테스트는 MySQL 컨테이너가 필요한 마이그레이션 테스트를 포함하지 않는다.
- `mysqlMigrationTest` 검증 작업은 MySQL 8.4 컨테이너에서 성공 이전과 모든 정합성 실패 시나리오를 실행한다.
- Docker 실행 환경을 사용할 수 없으면 전용 검증 작업은 건너뛰지 않고 실패한다.
- Pull Request 빌드가 전용 검증 작업에 실패하거나 실행하지 못한 상태에서는 병합하지 않는다.

## 실패 처리

V15의 데이터 검증은 스키마 변경보다 먼저 실행된다. 검증 오류로 실패하면 기존 avatar 컬럼은 유지되므로 실패 유형에 해당하는 원본 데이터를 바로잡고 다시 적용한다.

MySQL DDL은 트랜잭션으로 완전히 되돌릴 수 없다. 데이터 검증 이후 컬럼 추가, 백필, NOT NULL, 인덱스 또는 컬럼 제거 단계에서 실패하면 자동 재시도 전에 실제 스키마 상태를 확인한다. 부분 적용 상태에서 임의 SQL로 진행하지 않고 백업 복구 또는 검증된 Flyway 복구 절차를 선택한다.

다음 행위는 허용하지 않는다.

- 미일치 사용자를 임의의 기본 캐릭터에 연결
- 중복 일치 중 가장 작은 ID를 자동 선택
- `character_id`를 nullable로 남긴 채 서비스 재개
- avatar 제거 전에 백업과 백필 결과 확인을 생략
- 다른 Context 테이블을 직접 조회하도록 User Application을 우회

## 배포 후 확인

- 전체 사용자 수와 non-null `character_id` 사용자 수가 같다.
- `users.avatar` 컬럼이 존재하지 않는다.
- `idx_users_character_id` 인덱스가 존재한다.
- `users.character_id`에 Character 테이블 외래 키가 존재하지 않는다.
- 저장된 모든 `character_id`가 Character 공개 조회 계약으로 해석된다.
- 사용자 목록 조회가 사용자별 Character 쿼리를 반복하지 않는다.
- 참조 누락 시 아바타 null 응답이 아니라 RFC 9457 Problem Details 기반 내부 오류로 실패한다.

## 롤백

avatar 컬럼 제거 후에는 역마이그레이션으로 경로를 재구성하지 않는다. 점검 시간 안에 문제가 발견되면 쓰기 트래픽을 다시 열지 않고 사전 백업으로 데이터베이스와 Flyway 이력을 함께 복구한 뒤 이전 애플리케이션을 재기동한다.

복구 후에는 장애 원인, 부분 적용 여부, 백업 시점과 데이터 손실 가능성을 기록한다.

# Google 로그인과 단계별 회원가입

- Status: 구현 계약, 기본 비활성화
- Audience: 백엔드 개발자
- Source of Truth: Yes
- Last Reviewed: 2026-09-07

## 가입과 기존 계정

이메일·비밀번호 로그인을 유지하면서 Google 로그인을 제공한다. 신규 가입은 인증 → 필수 동의 → 닉네임·캐릭터 설정 순서다. 화면 제출 단위로 API를 제공하며, 페이지 진입이나 입력 변경으로 가입 레코드·이벤트를 발행하지 않는다.

인증 성공 후 DB에 10분짜리 가입 증명을 저장한다. 이 단계에는 아직 회원이 없다. 이메일을 확보하고 필수 약관에 동의하면 하나의 DB 트랜잭션에서 실제 User, 동의 기록, 필요한 Google 연결을 생성하고 증명을 소비한다. 최초 닉네임은 고유한 `가입대기_` 접두어를 사용하며, 캐릭터는 Character 카탈로그의 `base_image_1.webp`에 대응하는 실제 ID를 참조한다. 기본 캐릭터가 없거나 모호하면 회원 생성 전체를 취소한다.

회원 생성 후 상태는 `REQUIRED`다. 닉네임을 3분간 점유한 뒤 닉네임과 캐릭터를 함께 제출하면 `COMPLETED`로 전이한다. 기본 캐릭터를 그대로 선택해도 된다. 임시 닉네임을 최종 닉네임으로 선택할 수 없다. 회원 생성 후 프로필 완성에는 가입 증명의 10분 제한이 적용되지 않는다. 중단한 회원은 보존되며 다음 로그인에서 같은 userId로 재개한다.

기존 회원은 마이그레이션에서 `COMPLETED`가 된다. 탈퇴 시각을 변경하거나 과거 약관 동의 기록을 만들어내지 않는다. 기존 회원의 Google 연결은 재동의를 요구하지 않는다.

## Google 연결 규칙

검증된 `(provider, provider_subject)` 연결을 먼저 조회한다. 연결이 존재하면 그 회원을 사용하고 제공자의 이메일 변경으로 회원 이메일을 바꾸거나 다른 회원에 재연결하지 않는다.

연결이 없는 Google 신원은 검증된 Gmail과 기존 이메일이 일치할 때 기존 회원에 자동 연결할 수 있다. 기존 이메일 계정의 인증 가입 이력이 확인되었다는 운영 설정이 필요하다. 비밀번호가 없는 계정, 탈퇴 계정, 다른 Google 계정과의 연결 충돌은 자동 연결 대상에서 제외한다. Gmail의 영문 대소문자는 비교할 수 있지만 점과 `+tag`는 제거하지 않는다. 느슨한 DB 문자열 비교 결과만으로 연결하지 않는다.

일반 외부 이메일의 일치만으로 자동 연결하지 않는다. 충돌한 기존 회원은 기존 로그인 후 비밀번호를 다시 확인하는 명시적 연결 요청을 사용한다. 연결 목적과 대상 회원은 서버가 최초 요청에 묶고 콜백이 제출한 회원 ID를 받지 않는다.

신규 소셜 회원의 이메일이 없거나 제공자가 보증하는 검증 조건을 충족하지 않으면 같은 가입 증명에서 이메일 코드 인증을 완료한다. 인증된 이메일을 수정하면 새 이메일 검증 전에는 동의를 완료할 수 없다. 최종 이메일은 기존 허용 도메인 정책도 만족해야 한다.

Google로 신규 생성한 회원은 비밀번호가 없다. 비밀번호 재설정으로 비밀번호를 추가할 수 없으며 Google 로그인을 사용한다. 기존 이메일 회원에 Google을 연결하면 두 로그인 방법을 유지한다.

## 데이터와 트랜잭션

| 데이터 | 소유와 제약 |
| --- | --- |
| `users.profile_setup_status` | User가 소유하는 `REQUIRED` / `COMPLETED` 상태 |
| `signup_authentications` | 가입 증명·호출자 해시, 인증된 이메일, 임시 비밀번호 해시, 고정 만료 시각, 소비 결과와 재요청 지문 |
| `user_oauth_accounts` | 제공자+subject 고유, 회원+제공자 고유. subject는 대소문자·공백을 임의 정규화하지 않음 |
| `user_agreements` | 실제 동의한 문서 종류·버전·내용·동의 여부·시각 |
| `verification`의 가입 challenge | 요청·호출자·목적·소셜 증명 결합, 시도 횟수, 발송 및 재발송 상태 |
| `nickname_holds` | 닉네임·회원 고유, 고정 3분 만료. 회원당 하나의 예약 |
| `nickname_write_mutex` | 기존 가입·프로필 변경·신규 점유·가입 완료에서 사용자가 선택한 닉네임 경쟁을 직렬화 |
| `oauth_authorization_requests` | state/호출자 해시, 암호화된 nonce·PKCE verifier, 목적·대상·기기·등록 정보·상태·만료 |
| 발송·OAuth 요청 제한 테이블 | 새 요청 ID를 만들어도 우회하지 못하는 이메일/호출자 및 요청 출처 제한 |

가입의 영속 상태와 정확성은 DB에 의존한다. Redis 장애로 가입 증명·회원·닉네임 점유가 유실되는 구조를 사용하지 않는다. DB 장애 시 가입 쓰기는 실패하며 다른 저장소로 임의 우회하지 않는다.

동의는 회원·동의·소셜 연결·증명 소비를 함께 커밋한다. 같은 증명과 같은 동의 내용의 재시도는 같은 회원으로 복구된다. 다른 내용으로 소비된 증명을 재사용하지 않는다. 프로필 완료는 닉네임 검증·회원 변경·완료 상태·예약 해제를 함께 커밋한다. 같은 최종 값의 재시도만 성공으로 취급한다.

닉네임 비교는 기존 MySQL `users.nickname`의 대소문자·악센트 비교와 일치한다. 같은 예약을 다시 확인해도 만료 시각을 연장하지 않는다. 다른 닉네임 예약에 실패하면 이전 예약을 유지한다. 일반 프로필 수정과 구형 가입도 동일한 DB 잠금에 참여한다.

서버 생성 임시 닉네임은 일반 선택을 금지한 별도 접두어를 사용하므로 위 예약 경쟁에 참여하지 않는다. 임시 닉네임끼리의 충돌은 DB 고유 제약과 전체 생성 트랜잭션의 제한된 재시도로 처리한다.

## 인증 경계와 접근 제어

Google 검증 어댑터는 공식 SDK의 서명·발급자·시간 검증과 명시적인 audience·authorized party·nonce 검증을 수행한다. 웹은 state와 PKCE S256, 모바일은 서버가 발행한 nonce와 등록 이름을 결합한다. 클라이언트가 임의 audience를 지정하지 않는다.

OAuth 요청은 짧은 트랜잭션에서 `PENDING` → `PROCESSING`으로 선점한 뒤 외부 교환을 수행한다. 네트워크 호출 동안 DB 트랜잭션을 유지하지 않는다. 성공은 `CONSUMED`, 실패는 `FAILED`가 되며 재사용하지 않는다. 네트워크 결과가 불명확하거나 처리 중 중단되면 새 로그인을 시작한다. 외부 제공자에 대한 exactly-once 보장은 하지 않는다.

User의 Application 유스케이스가 인증·가입·세션 발행을 조정한다. Security는 공개 User 조회 계약으로 현재 상태를 확인하고 토큰/HTTP 접근 제어를 담당한다. Character는 기본 캐릭터 해석을 소유하며 User가 임의 숫자 ID를 만들지 않는다. 웹·모바일의 쿠키·헤더·본문 차이는 HTTP 입력 어댑터에서 처리한다.

`REQUIRED`는 자신의 상태, 가입 프로필·닉네임, 기본 캐릭터 목록, 로그아웃·재발급·가입 중 탈퇴와 기존 공개 읽기만 이용한다. 회원 전용 쓰기, 푸시 등록, SSE 등의 경로는 완료 전 차단한다. 회원 전용 요청은 DB의 최신 완료 상태를 확인한다. 탈퇴 회원은 로그인·재발급에서 제외한다.

프로필 설정 전 회원은 공개 프로필, 검색, 다른 Context에 제공하는 회원 참조·요약과 활성 회원 집계에서 제외한다. ID를 직접 지정해도 공개 프로필을 반환하지 않는다. 누적 가입 통계에는 실제 생성된 회원으로 포함하며 본인의 인증·가입 재개 조회는 유지한다. 프로필을 완료하면 같은 userId로 공개 조회에 참여한다.

## 운영과 전달 범위

신규 가입과 Google 인증은 기본 비활성화다. 실제 Google 등록, 약관 문서와 버전, 암호화 키, 웹 복귀 주소, 기본 캐릭터를 준비한 후 활성화한다. 신규 가입을 중지해도 Google 인증 기능이 활성화되어 있으면 이미 연결된 Google 회원의 로그인은 유지한다.

소셜 계정 테이블은 Apple·Naver·Kakao 같은 후속 제공자를 수용할 수 있다. 이번 구현에서 검증 어댑터와 실제 API 지원은 Google뿐이다. 제공자 추가 시 이메일 보증, subject 범위, 토큰 검증, 연결 해제·회수 정책을 별도 정의해야 한다.

프론트·모바일 저장소의 구현 작업은 이 문서 범위에 포함하지 않는다.

# Engineering Workflow

- Status: Active
- Audience: Engineers
- Source of Truth: Yes
- Last Reviewed: 2026-04-13

## 목적

이 문서는 `piku-back` 저장소에서 커밋, 리뷰, 테스트 작업을 수행할 때 따라야 하는 기본 엔지니어링 워크플로를 정의한다.

## 커밋 규칙

### 타입

| 타입       | 설명                                                |
| ---------- | --------------------------------------------------- |
| `feat`     | 새로운 기능 추가                                    |
| `fix`      | 버그 수정                                           |
| `docs`     | 문서 수정                                           |
| `style`    | 코드 포맷팅, 세미콜론 누락 등 코드 변경이 없는 경우 |
| `refactor` | 코드 리팩토링                                       |
| `test`     | 테스트 코드, 리팩토링 테스트 코드 추가              |
| `chore`    | 빌드 업무 수정, 패키지 매니저 수정                  |

### 형식

```text
<타입>: <설명>
```

- 스코프(`()`)는 사용하지 않는다.
- 설명은 수행한 작업의 목적과 행위가 드러나야 한다.

### 필수 규칙

1. 파일명을 커밋 메시지에 나열하지 않는다.
2. `Phase 3`, `Phase 9` 같은 내부 작업 단위 명칭을 쓰지 않는다.
3. `주제: ~~` 형태의 모호한 표현을 쓰지 않는다.
4. `git add -A` 또는 `git add .`를 쓰지 않고, 작업한 대상 파일만 명시적으로 추가한다.

## 리뷰 규칙

### API 오류 응답 원칙

- 새로 추가되거나 변경되는 API 오류 응답은 RFC 9457 / Problem Details 원칙을 따라야 한다.
- 문자열 body를 직접 반환하는 오류 응답은 기본적으로 리뷰 지적 사항이다.
- 모듈 내부 전용 ad hoc error DTO를 새로 만드는 경우는 기본적으로 리뷰 지적 사항이다.
- 기존 Problem Details 전환 흐름과 무관한 새로운 오류 응답 형식을 추가하는 경우는 기본적으로 리뷰 지적 사항이다.

### 예외 허용 조건

- 아래 조건을 모두 만족할 때만 임시 예외를 허용한다.
- 하위 호환이 명확하게 필요하다.
- 왜 예외가 필요한지 설명할 수 있다.
- 최종적으로 Problem Details로 수렴하는 전환 경로가 문서나 계획에 남아 있다.

### 리뷰 시 확인 항목

- 상태 코드는 적절한가
- 오류 응답이 `ProblemDetail` 또는 이에 준하는 공용 생성 경로를 사용하는가
- `status`, `detail`이 일관되게 내려가는가
- `instance`, `type` 같은 필드를 쓰는 경우 프로젝트 규칙과 맞는가
- 기존 클라이언트 호환 때문에 예외를 두었다면 범위가 최소화되어 있는가
- DDD + 헥사고날 아키텍처 경계를 존중하는가
- 애플리케이션 계층이 웹, DB, 외부 인프라 세부사항에 직접 결합되지 않는가
- 포트와 어댑터 책임이 적절히 분리되어 있는가
- 변수명, 메서드명, DTO명, 포트명이 역할과 의미를 명확하게 드러내는가

## 테스트 규칙

### 테스트 구조

- `// given`, `// when`, `// then` 주석을 사용하지 않는다.
- 대신 빈 줄로 섹션을 구분한다.
- `@ExtendWith(MockitoExtension.class)` 사용을 기본으로 한다.
- `@Nested` + `@DisplayName`으로 메서드별 그룹핑을 선호한다.
- AssertJ (`assertThat`)를 사용한다.
- BDDMockito (`given`, `then`)를 사용한다.

### API 응답 테스트 규칙

- API 오류 응답을 변경하거나 추가할 때는 RFC 9457 / Problem Details 형식을 기본으로 검증한다.
- 최소 검증 항목은 `status`, `detail`이다.
- `instance`, `type` 같은 필드를 사용한다면 함께 검증한다.
- 하위 호환 때문에 임시 예외를 둘 경우, 왜 예외가 필요한지와 최종적으로 Problem Details로 수렴할 계획을 테스트 또는 문서에서 드러내야 한다.
